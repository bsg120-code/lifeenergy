# 🎨 라이프이엔지 시스템 디자인 패키지 v3.0: 데이터 필터링 아키텍처 (Deep Red $\to$ Cyan Blue)

**작성 목적:** PoC 무료 진단 페이지의 핵심 인터랙션 컴포넌트(RawData, FilterArray, CleanOutput)를 개발팀에 전달하는 최종 개발 가이드라인 및 API 명세서.
**적용 범위:** 모든 프론트엔드/백엔드 엔지니어링 팀 (FE/BE).
**버전:** 3.0.0
**핵심 원칙:** Deep Red $\to$ Cyan Blue의 감정적 전환을 기술적으로 '데이터 필터링 및 구조화' 과정으로 치환하여 사용자에게 통제감을 부여한다.

---

## 📂 I. 개요 및 아키텍처 플로우 (The System Flow)
### 1. 핵심 목표: 통제력 확보의 시각화 [근거: Designer 검증된 지식]
이 컴포넌트는 단순한 색상 변화가 아니라, '무질서하고 과부하된 데이터(Deep Red)'가 시스템 필터링 과정을 거쳐 '정밀하게 구조화된 KPI 대시보드(Cyan Blue)'로 전환되는 **기술적 스토리텔링**을 구현하는 것이 핵심입니다.

### 2. 전반적인 사용자 경험 (UX Flow)
1.  **[Phase 1: Deep Red - 위기]**: 사용자가 '문제점' 데이터에 노출됨. 무작위의, 과부하된 원시 로그(Raw Data Stream)가 화면을 가득 채움. ($\text{Deep Red} \to$ 혼란).
2.  **[Phase 2: Transition - 과정]**: 시스템이 개입함. '시스템 필터 배열(Filter Array)' 컴포넌트가 활성화되며, 노이즈를 제거하고 핵심 지표만 추출하는 애니메이션을 보여줌. ($\text{Accent Yellow} \to$ 집중).
3.  **[Phase 3: Cyan Blue - 통제]**: 정제된 결과물(Clean Output)이 KPI 대시보드로 명확하게 표시됨. 사용자는 '우리가 시스템을 통제했다'는 안도감과 권위감을 느낌. ($\text{Cyan Blue} \to$ 안정).

## 💾 II. 컴포넌트별 데이터 스펙 (JSON Schema Integration)
본 패키지는 세 개의 독립적이지만 순차적으로 의존하는 데이터 구조를 가집니다. (세부 JSON 스키마는 별도 파일로 참조, 여기서는 필드 명만 정의합니다.)

### 1. Component A: RawData Stream (입력 단계 - Deep Red)
*   **역할:** 비정형적이고 과부하된 원시 데이터 시뮬레이션.
*   **데이터 구조 특징:** 시간 순서(Timestamp), Source ID, Error Code 등 정규화되지 않은 JSON 배열 형태를 취함.
*   **주요 필드 (Schema Reference):** `timestamp` (ISO 8601), `source_id` (String), `error_code` (Array of String), `data_payload` (Object).

### 2. Component B: Filter Array (처리 단계 - Transition)
*   **역할:** RawData를 필터링하고 구조화하는 논리적 과정 시각화.
*   **데이터 구조 특징:** 입력 데이터에 대한 '처리 행위' 기록을 저장하며, 어떤 로직(Rule Set)이 적용되었는지를 추적해야 함 (Auditability).
*   **주요 필드 (Schema Reference):** `rule_applied` (String: e.g., 'Anomaly Detection', 'Frequency Filter'), `filtered_count` (Integer), `pass_through_data` (Object/Array of Object).

### 3. Component C: Clean Output Dashboard (출력 단계 - Cyan Blue)
*   **역할:** 필터링 과정을 거쳐 확보된 핵심적인 KPI와 통제 결과물을 명확하게 제시.
*   **데이터 구조 특징:** 정규화되고 해석 가능한 최종 데이터셋. 모든 수치는 측정 단위(Unit)를 포함해야 함.
*   **주요 필드 (Schema Reference):** `kpi_metric` (String), `current_value` (Float/Integer), `unit` (String: e.g., 'M USD', '%'), `baseline_comparison` (Object).

## ⚙️ III. API 엔드포인트 및 개발 가이드라인 (Developer Handoff)
개발팀이 이 시스템을 구현하기 위해 필요한 백엔드/프론트엔드 인터페이스를 정의합니다. 모든 요청은 인증(Auth Token) 처리가 필수입니다.

### 1. A. RawData 수집 API (POST Request)
*   **Endpoint:** `POST /api/v3/data/raw`
*   **기능:** 클라이언트가 시뮬레이션할 원시 데이터 스트림을 서버로 전송하는 엔드포인트. (시각적 노이즈 생성 트리거).
*   **Request Body (JSON):** `{ "client_session_id": "UUID", "raw_data_batch": [/* RawData Array */] }`
*   **Response:** `{ "status": "success", "request_id": "uuid-1234" }`

### 2. B. Filter 처리 요청 API (POST Request)
*   **Endpoint:** `POST /api/v3/process/filter`
*   **기능:** RawData를 기반으로 필터링 및 구조화 처리를 요청합니다. 이 API 호출이 **Deep Red $\to$ Cyan Blue 전환의 핵심 트리거**가 됩니다.
*   **Request Body (JSON):** `{ "request_id": "uuid-1234", "filter_rule_set": ["Rule A", "Rule B"] }`
*   **Response:** `{ "status": "processing", "job_id": "job-xyz", "message": "Filtering started. Check status endpoint." }`

### 3. C. 결과 조회 API (GET Request)
*   **Endpoint:** `GET /api/v3/result/{job_id}`
*   **기능:** 필터링 처리가 완료된 후, 최종 구조화된 KPI 데이터를 클라이언트에 제공합니다.
*   **Request Parameters:** `?job_id=job-xyz`
*   **Response (JSON):** `{ "status": "completed", "final_data": [/* CleanOutput Array */] }`

---
### 💡 기술적 구현 권고 사항 (개발팀 참고)
1.  **Deep Red $\to$ Cyan Blue 전환 로직:** `POST /api/v3/process/filter` 호출 시, **비동기 백엔드 작업(Async Background Job)**을 실행하고, 이 과정 동안 프론트엔드는 *로우 데이터가 필터되는 애니메이션*(`FilterArray`)만을 보여주어야 합니다.
2.  **성능:** RawData의 볼륨이 커질 경우, 서버 부하 관리를 위해 **Streaming API**를 고려해야 하며, `job_id` 기반의 상태 관리(State Management)를 철저히 할 것.
